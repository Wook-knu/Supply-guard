# 프론트엔드 작업 정리 (2026-08-01)

## 작업 범위

이번 변경은 배포 환경이 아닌 `feature/frontend` 브랜치의 로컬 작업으로 진행했다.
사용자 핵심 흐름인 **품목 검색 → 품목 관리 → 신규 품목 분석 → 추천 확인 → 추천 피드백 저장**을 연결하고, 린트·타입 검사·빌드 명령을 정비했다.

## 완료한 작업

### 1. 대시보드 검색

- `api.getQueries()`와 `api.getRisks()` 응답을 클라이언트에서 조합한다.
- 품목명, HS 코드, 국가명, 국가코드 부분 일치를 지원한다.
- 검색 결과에 품목명·HS 코드와 국가별 SGRI를 표시한다.
- 결과 선택 시 `/risks/{hs_code}`로 이동한다.
- 검색 데이터의 로딩·오류·결과 없음·재시도 상태를 처리한다.
- 기존 리튬 품목명 하드코딩을 제거하고 API의 품목명을 사용한다.

### 2. 품목 목록·관리 `/items`

- 로그인 사용자의 등록 품목을 `api.getQueries()`로 조회한다.
- 품목별 `api.getRisks(hsCode)` 결과에서 최신 최고 SGRI를 계산한다.
- 품목명, HS 코드, 최고 SGRI, 위험 배지, 등록일을 표시한다.
- 리스크 상세, 추천, 보고서 작성 페이지로 `query_id`와 HS 코드를 유지해 이동한다.
- 삭제 확인과 `api.deleteQuery()` 연결, 삭제 중 상태, 실패 상태를 처리한다.
- 목록 로딩·오류·빈 상태를 처리한다.

### 3. 신규 품목 등록 후 SGRI 분석 `/items/new`

- 예시 품목·HS·국가 초기값을 제거했다.
- 품목 등록과 SGRI 분석 실행을 2단계로 분리했다.
- HS 코드를 숫자로 정규화하고 최소 길이를 검증한다.
- 품목 등록 성공 후 입력값을 잠그고 `이 품목 분석 시작` 버튼을 표시한다.
- `api.buildItemSgri(hsCode)`로 분석 작업을 시작한다.
- `api.getBuildJob(jobId)`를 약 1.5초 간격, 최대 약 60초 동안 폴링한다.
- 진행 중 스피너·경과 진행률과 중복 클릭 방지를 적용한다.
- 완료 시 API의 `result.countries`를 표시하고 `/recommendations?query_id={id}`로 유도한다.
- 국가 결과 0개, 작업 오류, 시간 초과와 재시도 상태를 처리한다.

### 4. 추천 피드백 실제 저장 `/recommendations`

- 국가·공급사 추천의 하드코딩 fallback 데이터를 제거했다.
- 품목, 국가 추천, 공급사 추천을 실제 API에서 함께 조회한다.
- 추천 데이터의 로딩·오류·빈 상태·재시도를 처리한다.
- 국가 추천 응답의 `reco_id`를 선택된 추천과 연결한다.
- `도움 됐어요`는 `rating: 1`, `도움이 안 됐어요`는 `rating: -1`로 `POST /feedback`에 저장한다.
- 저장 중 중복 클릭 방지, 저장 성공, 저장 오류를 표시한다.
- 백엔드 국가 추천 응답에 ORM의 `id`를 `reco_id`로 반환하도록 스키마를 보강했다.

### 5. API와 개발 검증 환경

- `api.deleteQuery()`, `api.buildItemSgri()`, `api.getBuildJob()`, `api.sendFeedback()`를 추가했다.
- `204 No Content` 응답을 JSON 파싱하지 않도록 공통 `http()`를 보완했다.
- `npm run typecheck` 명령과 ESLint 9 flat config를 추가했다.
- Tailwind 플러그인을 ESM import로 변경해 린트 오류를 제거했다.

## 검증 결과

- `npm run typecheck`: 통과
- `npm run lint`: 오류 0개, 기존 미사용 import 경고 18개
- `npm run build`: 통과
- 브라우저 검색 검증: 품목명, HS 코드, 국가코드 검색과 리스크 이동 확인
- 품목 관리 검증: 리스크·추천·보고서 링크와 삭제 요청 확인
- 피드백 검증: 긍정·부정 요청 본문과 성공 상태 확인
- 실제 로컬 FastAPI·PostgreSQL 검증:
  - 로그인 `200 OK`
  - 품목 등록 `201 Created`
  - SGRI 작업 시작 `202 Accepted`
  - 작업 상태 폴링 후 `done`
  - 추천 URL에 생성된 `query_id` 유지
  - 품목 목록에 신규 품목 저장 확인

실제 로컬 검증에서는 Comtrade 원천 데이터와 API 키가 없어 분석 결과가 `countries: 0`이었다. 프론트는 이를 완료 후 빈 결과 상태로 정상 처리했지만, 국가 추천 데이터가 생성되는 전체 시나리오는 데이터 수집 환경이 준비된 뒤 다시 확인해야 한다.

## 후속 회의가 필요한 사항

### 1. 부정 피드백 이후 재추천 정책

현재 `도움이 안 됐어요`는 부정 평가만 저장하며 순위를 다시 계산하지 않는다.

- 기존 1위 국가를 자동으로 제외할지
- 사용자가 제외 국가를 직접 선택하게 할지
- 가격·납기·위험도 조건을 수정한 뒤 재추천할지
- 재추천 전용 백엔드 API와 요청 형식을 어떻게 정의할지

### 2. 대시보드 검색 범위

현재 검색은 로그인 사용자의 등록 품목과 해당 품목의 국가 리스크만 대상으로 한다.

- 검색 결과에서 리스크와 추천 중 어느 화면을 기본 이동 대상으로 할지
- 국가 검색 시 관련 품목을 묶은 중간 결과 화면이 필요한지
- 전체 글로벌 품목 탐색을 별도 `/explore` 기능으로 제공할지
- 글로벌 탐색용 데이터와 검색 API를 별도로 구축할지

### 3. 알림 설정 저장 API

`/settings`의 알림 토글은 아직 화면 상태만 변경한다.

- `GET /alert-settings`와 `PUT /alert-settings` 제공 시점
- 고위험 기준값을 사용자별로 저장할지, 요금제별로 제한할지
- 이메일·앱 알림 등 채널별 설정 범위

### 4. 신규 품목 데이터 수집 운영

- Comtrade API 키를 로컬·배포 환경에 누가 설정하고 관리할지
- 일부 연도 수집 실패 시 완료로 볼지, 부분 성공으로 표시할지
- `countries: 0`을 정상 완료로 볼지 데이터 부족 오류로 볼지
- 60초를 넘는 작업을 화면 재접속 후에도 이어서 확인할 수 있도록 job id를 저장할지

### 5. 실행 중 발견된 데이터·환경 문제

- 신규 로컬 DB에서는 품목 등록일이 `등록일 없음`으로 표시되어 `QueryOut.created_at`과 DB 컬럼 매핑 확인이 필요하다.
- Apple Silicon 로컬 Docker 백엔드는 시작 시 `Illegal instruction`으로 종료되어 Python 3.12 로컬 실행으로 우회했다. Docker 이미지의 Python·NumPy/Pandas 호환성을 팀에서 확인해야 한다.
- 실제 추천·피드백 전체 검증을 위해 국가 추천 시드 또는 Comtrade 수집 성공 데이터가 필요하다.
